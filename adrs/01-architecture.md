## Контекст
Створюється вебзастосунок, що складається з клієнтської та серверної частини, потрібно визначити структуру репозитарію для швидкого прототипування та легкого узгодження контрактів api.

## Варіанти що розглядались
### Монорепозиторій з окремими frontend та backend
**Переваги**
- спільна історія змін і один pr
- можливість повторного використання типів, dto, валідаційних схем через окремий локальний пакет
- зручна розробка для одного розробника/невеликої команди\

**Недоліки**
- ризик потрапляння серверної логіки на frontend
- необхідність налаштування залежностей, правил імпорту\

### Окремі репозиторії для frontend і backend
**Переваги**
- незалежні версії, пайплайни збірки та релізу
- ізоляція оточень, конфігурацій та залежностей
- зручна розробка для більшої команди\

**Недоліки**
- контроль узгодження змін api та перевірка сумісностей клієнта з сервером
- дублювання спільних типів
- більше адміністративної роботи 

## Прийняте рішення
Монорепозиторій з окремими frontend та backend:
зручно як для самого процесу розробки так і з точки зору організації залежностей у невеликому mvp-проєкті 

## Наслідки
- Зміни api можуть узгоджуватись в межах одного pr
- Локальний запуск і перевірка застосунку спрощуються
- Необхідно налаштувати npm workspaces, визначити межі пакетів та правила імпорту
- Заборонити імпорт серверної реалізації на frontend
- Зберігати в спільному пакеті лише код, який безпечно використовувати на клієнті
- Перевіряти сумісність api автоматизованими тестами або перевірками контрактів.
